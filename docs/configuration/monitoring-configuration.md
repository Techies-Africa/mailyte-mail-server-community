# Monitoring Configuration

Metric endpoints, the shipped alert rules, and Alertmanager routing.

---

Mailyte's monitoring has two layers: **Prometheus** scraping every worker's `/metrics` endpoint (plus the MySQL and Redis exporters), and the **monitoring worker service**, which actively health-checks services, publishes backup-freshness gauges, auto-heals containers through the docker-socket proxy, and emits `health.*` webhooks.

## Metric Endpoints

Add the exporters yourself (and re-enable the commented jobs/rules) if you want queue-depth and host metrics in Prometheus.

## The Monitoring Worker

`worker/monitoring` (port 8085) is a producer, not a scraper replacement:

- **Service health checks** — HTTP and protocol-level (SMTP/IMAP) probes; state transitions emit `health.service.down` / `health.service.up` webhooks.
- **Auto-heal** — restarts unhealthy containers through the scoped socket proxy (`DOCKER_HOST=tcp://docker-proxy:2375`), emitting `health.recovery`.
- **Backup monitor** — publishes `monitoring_backup_age_seconds`, `monitoring_backup_last_status`, `monitoring_backup_last_size_bytes`, `monitoring_backup_unencrypted_runs` (labels `host`, `backup_type`) from the `backup_history` table. `BACKUP_EXPECTED_HOSTS` declares which hosts must report.
- **System alerts** — CPU/memory/bounce-rate/SLA thresholds emit `health.system.alert` webhooks.

## Shipped Alert Rules

Rules live in `monitoring/prometheus/rules/` (mounted read-only into Prometheus).

### `mail_alerts.yml`

Active rules (every live expression matches a real series as of the 2026-08-30 cleanup):

| Alert | Expression | For | Severity |
|-------|-----------|-----|----------|
| ServiceDown | `up == 0` | 2m | critical |
| HighErrorRate | `sum by (job) (rate({__name__=~".+_http_errors_total"}[5m])) / sum by (job) (rate({__name__=~".+_http_requests_total"}[5m])) > 0.05` | 5m | warning |
| DatabaseConnectionPoolExhausted | mysql threads_connected / max_connections > 0.80 | 5m | warning |
| SlowQueries | `rate(mysql_global_status_slow_queries[5m]) > 10` | 10m | warning |
| RedisMemoryHigh | used/max > 0.80 | 10m | warning |

> [!NOTE]
> `HighErrorRate` sweeps the service-prefixed counters via a `__name__` regex, because every service metric carries its service prefix (e.g. `api_http_errors_total`) and the bare name matches nothing. The rules whose series have **no producer at all** — MailQueueBackup/Critical and the bounce-rate pair (`postfix_*`, no Postfix exporter), DiskSpaceWarning/Critical (`node_filesystem_*`, no node-exporter), KafkaConsumerLag (kafka-exporter not deployed), and BruteForceDetected/DLPViolation (`auth_failures_total` / `dlp_violations_total` never exported) — are commented out in `mail_alerts.yml` with dated notes; restore each alongside its producer.

### `backup_alerts.yml`

These are written against real series and all function:

| Alert | Fires when | Severity |
|-------|-----------|----------|
| NoRecentFullBackup | `monitoring_backup_age_seconds{backup_type="full"} > 93600` (26 h) | critical |
| NoRecentIncrementalBackup | `> 7200` (2 h) | warning |
| BackupMonitoringGone | `absent(monitoring_backup_age_seconds)` for 15m | critical |
| BackupLastRunFailed | last run incomplete on a host that has succeeded before | warning |
| BackupNeverRun | age at the 10-year sentinel for 1 h | critical |
| UnencryptedBackupsPresent | `monitoring_backup_unencrypted_runs > 0` | warning |
| ArchiveSpoolNotDraining / ArchiveSpoolBacklogCritical | `archiver_archive_spool_depth > 0` (30m) / `> 5000` (15m) | warning / critical |
| ArchiveStoreFailing | `rate(archiver_archive_store_failures_total[15m]) > 0` | critical |

They alert on **absence** deliberately — a backup that quietly stopped running produces no errors, only rising age.

## Alertmanager

`monitoring/alertmanager/alertmanager.yml` routes **everything to the webhooks service** (`POST /alertmanager`, added 2026-08-30), which forwards each alert through the global webhook dispatcher as signed `system.alert.firing` / `system.alert.resolved` events to `WEBHOOK_URL`:

```yaml
route:
  receiver: 'webhook-notifications'
  group_by: ['alertname', 'severity']
  group_wait: 30s
  group_interval: 5m
  repeat_interval: 4h
  routes:
    - receiver: 'critical-alerts'
      match: { severity: critical }
      group_wait: 10s
      group_interval: 1m
      repeat_interval: 1h

receivers:
  - name: 'webhook-notifications'
    webhook_configs:
      - url: 'http://webhooks:8081/alertmanager'
        send_resolved: true
  - name: 'critical-alerts'
    webhook_configs:
      - url: 'http://webhooks:8081/alertmanager'
        send_resolved: true
```

Inhibit rules: critical suppresses warning for the same `alertname`; `ServiceDown` suppresses other alerts for the same `job`.

> [!WARNING]
> If your downstream of the webhooks service is email through Mailyte itself, you won't get alerts when Mailyte is down. Wire at least the critical route to an external channel (PagerDuty, Slack, etc.) by editing the receiver.

## Grafana

Provisioned from `monitoring/grafana/`: the Prometheus datasource (`http://prometheus:9090`) and two dashboards in the `Mailyte` folder — `mail_overview` and `security_dashboard`. Login: `GRAFANA_ADMIN_USER` (default `admin`) / `GRAFANA_ADMIN_PASSWORD`; sign-up disabled. In production, Grafana is published on `127.0.0.1:3000` and via Traefik at `grafana.$DOMAIN`.

## Key Health Checks That Don't Need Prometheus

```bash
./start.sh health                             # per-service health summary
docker exec postfix postqueue -p | tail -1    # queue depth
curl -s localhost:8083/health                 # API health (host port)
docker compose ps                             # container states
```
